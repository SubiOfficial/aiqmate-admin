## 4. MULTI-TENANT ARCHITECTURE

Implement a secure shared-database, shared-schema multi-tenant
architecture.

Every tenant must have logically isolated data.

The application must support:

-   Multiple tenants.
-   Multiple users per tenant.
-   Users belonging to multiple tenants.
-   Different roles for the same user in different tenants.
-   Tenant-specific assets.
-   Tenant-specific procedure usage.
-   Tenant-specific procedure pricing.
-   Tenant-specific invoices.
-   Tenant-specific payment history.
-   Tenant-specific subscriptions.
-   Platform-level Super Admin management.

### Tenant isolation requirements

Every tenant-owned record must be associated with the correct tenant.

Every tenant-scoped API must:

1.  Authenticate the logged-in user.
2.  Identify the active tenant.
3.  Verify the user's membership in that tenant.
4.  Validate the required role or permission.
5.  Apply tenant filtering to all database queries.
6.  Return only records belonging to the authorized tenant.

Never trust a tenant ID supplied by the frontend without validating
membership and authorization on the backend.

Prevent:

-   Cross-tenant data access.
-   Cross-tenant record modification.
-   Cross-tenant deletion.
-   Cross-tenant asset relationships.
-   Cross-tenant procedure billing.
-   Cross-tenant invoice access.
-   Cross-tenant payment access.
-   Cross-tenant pricing access.

Consider PostgreSQL Row-Level Security (RLS) as an additional security
layer.

If RLS is implemented, ensure tenant context is set safely for each
transaction and connection. Account for connection pooling, transaction
boundaries, and restricted database roles.

Do not rely on frontend filtering for tenant security.

## 7. TENANT-SPECIFIC CONFIGURABLE PROCEDURE PRICING

### 7.1 Mandatory business requirement

This is one of the most important requirements of the entire
application.

**Procedure pricing must be independently configurable for every
tenant.**

There must be:

-   No fixed pricing slabs.
-   No globally hardcoded procedure rates.
-   No assumption that all tenants use the same pricing.
-   No mandatory standard procedure count ranges.
-   No silent global fallback pricing.

Each tenant must have its own pricing configuration.

For example:

-   Tenant A may configure 1--100 procedures at one price and 101--500
    at another price.
-   Tenant B may configure 1--50 procedures at a different price and
    51--200 at another price.
-   Tenant C may configure completely different slabs, prices,
    currencies, and billing periods.

These are examples only. They must never be hardcoded into the
application.

### 7.3 Configurable pricing calculation methods

Support two pricing calculation methods.

Both must be configurable per tenant and pricing configuration.

#### Method A: Graduated / Tiered Pricing

Each slab's rate applies only to the procedures within that slab.

Illustrative example:

  Procedure range     Rate per procedure
  ----------------- --------------------
  1--100                          \$2.00
  101--500                        \$1.75
  501--1,000                      \$1.50
  1,001 onward                    \$1.25

If a tenant uses 600 billable procedures:

-   First 100 × \$2.00 = \$200
-   Next 400 × \$1.75 = \$700
-   Next 100 × \$1.50 = \$150

Total = \$1,050.

These ranges and amounts are illustrative only.

#### Method B: Volume Pricing

When total usage reaches a configured slab, that slab's unit price
applies to all eligible procedures in the billing period.

Using the same illustrative ranges, if 600 procedures are used:

-   Applicable slab rate = \$1.50.
-   600 × \$1.50 = \$900.

The UI must clearly explain the difference between Graduated/Tiered and
Volume Pricing.

Do not silently switch calculation methods.

### Pricing configuration rules

-   Each tenant can use a different calculation method.
-   Different procedure categories may use different configurations.
-   Pricing must be resolved using the correct tenant, procedure
    category, billing period, and effective date.
-   Prevent overlapping active pricing configurations for the same scope
    and period.
-   Prevent invalid or overlapping slab ranges.
-   Validate gaps in slab coverage according to the configured pricing
    rules.
-   If usage exceeds the highest configured slab and no applicable rate
    exists, return a clear pricing configuration error.
-   Never silently use another tenant's pricing or a global default.

## 9. AUTOMATIC USAGE CALCULATION AND BILLING ENGINE

Build a reliable backend billing engine integrated with procedure
execution.

The billing engine must:

1.  Identify the tenant.
2.  Identify the correct procedure and category.
3.  Identify the billing period.
4.  Retrieve the tenant's applicable pricing configuration.
5.  Validate its effective dates and status.
6.  Count eligible billable procedure executions.
7.  Apply the configured pricing calculation method.
8.  Resolve the applicable pricing slabs.
9.  Calculate the amount using exact decimal arithmetic.
10. Save the usage and pricing snapshot.
11. Generate the appropriate billing records.
12. Prevent duplicate charges.
13. Maintain audit history.

### Billing calculation requirements

Support both:

-   Graduated/Tiered Pricing.
-   Volume Pricing.

Use a single authoritative backend pricing calculation service.

Do not duplicate calculation logic in multiple controllers or frontend
components.

The pricing service must be reusable by:

-   Live pricing preview APIs.
-   Usage calculation.
-   Invoice generation.
-   Billing history.
-   Automated billing jobs.

The backend must return a detailed calculation breakdown.

### Billing period

Support configurable billing periods, including monthly or other
explicitly configured periods.

Do not assume every tenant must use the same billing period.

Handle:

-   Period start and end.
-   Time zones.
-   Month boundaries.
-   Late-arriving execution records.
-   Failed background jobs.
-   Repeated billing job execution.
-   Billing period closing.
-   Corrections and adjustments.

Use a consistent, documented billing timezone policy.

### Missing pricing

If pricing is not configured:

-   Return `PRICING_NOT_CONFIGURED`.
-   Do not silently apply a default rate.
-   Do not generate an incorrect invoice.
-   Record the configuration problem for administrative review.

If a usage quantity falls outside all configured slabs, return a clear
pricing coverage error and prevent incorrect billing.

### Billing adjustments

Any manual usage or billing adjustment must:

-   Require explicit authorization.
-   Record the reason.
-   Record the user who performed it.
-   Preserve the original usage record.
-   Create an auditable adjustment entry.
-   Preserve finalized invoice history.

Never silently modify previously billed usage.
